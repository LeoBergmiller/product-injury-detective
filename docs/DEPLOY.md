# Deploying to Cloud Run

Same convention as our Project 1: Cloud Run with continuous deploy from GitHub,
Google Cloud **buildpacks** (no Dockerfile), and the data shipped in the repo.

## Service settings

| Setting | Value | Why |
|---|---|---|
| Source | GitHub `LeoBergmiller/product-injury-detective`, branch `main`, continuous deploy (Developer Connect) | Handout requirement |
| Build type | Google Cloud buildpacks (Python), **no Dockerfile** | Project 1 deployed this way from `pyproject.toml` + `uv.lock` alone, with no `requirements.txt` |
| Entrypoint | `uvicorn app:app --host 0.0.0.0 --port $PORT` | Set in the build configuration's "Entrypoint" field, as in Project 1 |
| **Maximum instances** | **1** | Chat sessions live in memory; a second instance would not know the first one's sessions |
| Minimum instances | 0 (or 1 to avoid cold starts during grading) | Startup only opens DuckDB and reads two small JSON/MD files |
| **Request timeout** | **300 s or more** (we suggest 600) | Graders wait up to 5 minutes; one chat turn is capped at 240 s and 8 agent turns in `build/config.yaml` |
| Memory / CPU | 2 GiB, 1 vCPU (suggested; **not measured on Cloud Run**) | DuckDB scans the NEISS Parquet files per query |
| Concurrency | default (80) | Requests share one read-only DuckDB connection; each query uses its own cursor |
| Environment variables | none required | `AGENT_MODE=plain` is only for the README comparison; never set it on the service |
| Secrets | none | The deployed app does not call SaferProducts, so no `SAFERPRODUCTS_KEY` |

## Model access (Vertex AI, no API key)

- The app calls `vertex_ai/gemini-3.5-flash-lite` (location `global`) through litellm,
  authenticated with the service's **application default credentials**.
- Give the Cloud Run **service account** the role **Vertex AI User**
  (`roles/aiplatform.user`) in the project.
- The **Vertex AI API** must be enabled in the project.

## Data

- `data/processed/` is committed: 144 MB in total, and the largest file is 22 MB
  (under GitHub's 100 MB limit). It ships with the build, so no GCS bucket is needed.
- The app opens `data/processed/injuries.duckdb` read-only. The NEISS views read
  Parquet by repo-relative paths, which DuckDB only allows from the repo root, so
  `detective/db.py` changes the working directory to the repo root when it opens the
  database. The buildpack already starts in the repo root (`/workspace`).
- `data/processed/system_prompt.md` and `agent_context.json` are generated by
  `build/build_agent_context.py`. Commit them after every rebuild.

## Verified locally (2026-11-08)

This used a fresh copy of exactly the files git would commit (tracked plus
non-ignored), in a new directory:

```bash
uv sync --locked
.venv/bin/uvicorn app:app --host 0.0.0.0 --port 8080
```

Results:
- `GET /health` returned `{"status":"ok","mode":"detective"}`.
- `GET /` returned 200.
- `POST /clear` returned `{"status":"ok"}`.
- A live `POST /chat` ("How many ER visits were there for children under 5 in
  2025?") answered 1,469,070 in 4 s, using local gcloud ADC. Its response has
  `response`, `session_id`, `tool_calls` (each with `agent`), `table`, `chart`,
  `caveats`, and `mode`.
